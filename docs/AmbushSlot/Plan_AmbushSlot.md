## (완료) 결과 — 저작 없이 목표 달성 (2026-08-12)

**이 문서의 Step 1~8은 착수하지 않았고, 앞으로도 필요 없을 수 있다.** `Step -1`의 측정 루프만으로
요구 둘을 다 만족시켰다. 실측 다섯 번의 추이:

| 단계 | 발동/자격창 | 무엇을 바꿨나 |
|---|---|---|
| 노출 1초 고정 | 2/8 (25%) | `minRingExposure`·`maxRingExposure` = 1.0 |
| + 늦은 선정 | 3/10 (30%) | `HandleIdleWindow`에서도 후보를 한 번 더 고른다 |
| + `staged` 후보 확장 | 3/7 (43%) | `PickIdleAmbusher(includeStaged)` |
| + 쿨다운 3초 | 4/8 (50%) | `cooldown` 6 → 3 |
| **+ 보충 규칙** | **8/13 (62%)** | `ReinforceActiveIfThin` |

**곡당 8회(≈1.4분) = 2분 환산 11회.** 목표(2분에 5~8회)를 오히려 넘어, 이제는
**쿨다운이 빈도를 붙잡는 유일한 장치**다. 잦다고 느껴지면 `cooldown`을 4~5초로 올린다 —
자격 검사는 그대로라 **경고 1초는 유지된다.**

### 이 과정에서 확인된 사실

1. **경고 1초 고정은 검증됐다.** 모든 발동 로그가 `링 1.00s`이고 `임팩트까지`가 예외 없이 1.0 초과다.
   자격 검사(`RequiredLead = max(와인드업, minRingExposure)`)가 안전장치라
   **약속보다 짧게 보이는 경우가 구조적으로 안 생긴다.**
2. **병목은 시간이 아니라 인원이었다.** 착수 전 가설("채보가 시간을 안 준다")은 **틀렸다** —
   자격 창은 곡당 8~13개로 충분했고, 그 창에 기습할 적이 없었다.
3. **인원이 없던 이유는 §11-6의 구조였다.** `PickIdleAmbusher`는 `active`만 보는데,
   사망 보충은 `staged`로 들어가고 승격은 `active`가 빌 때만 일어난다 → `active`는 4→3→2→1로 마르고
   **1에 도달하면 그 1명이 현재 상대**다. 실측 "후보 없음" 19건 중 17건이 `active 1 · staged 3`이었다.
4. **거리는 증상이지 원인이 아니었다.** `staged`를 후보에 넣자 탈락 사유가 `화면밖`·`바쁨`으로 옮겨갔는데,
   둘 다 **집결지가 5.5~8m(= `cruiseSpeed × 창`)라서** 생긴 증상이다 —
   적 `moveSpeed` 3m/s로는 2.0~2.7초가 걸리는데 리드는 1.1초다.
5. **"먼가"가 아니라 "제때 닿는가"를 물어야 했다.** 집결지 거리는 창에 비례해 변하므로
   거리로 뭉뚱그려 막으면 가까울 때까지 버린다 → `canReach` 자격으로 교체.

### 최종 적용된 변경 (전부 `Step -1` 소속)

| 파일 | 변경 |
|---|---|
| `DodgeDirector` | `minRingExposure`/`maxRingExposure` = 1.0 · `cooldown` 3 · `StageAmbusher(includeStaged, arriveBy)` · `lateStageWindup` |
| `EnemyDirector` | `PickIdleAmbusher(includeStaged, canReach)` · `CollectAmbushCandidates` · `ReinforceActiveIfThin` · `ReleaseAmbusher`의 집결지 복귀 · `stagedMaxDistance`(8m) |

⚠ **`ReinforceActiveIfThin`은 무리 세대당 한 번만 부른다.** 계속 채우면 `active`가 0에 도달하지 못해
**승격이 영영 안 일어나고**, 다음 무리로 이동하는 §11-6의 리듬이 통째로 사라진다.
인원 불변식(`active + staged = clusterSize`)은 **합**에 대한 규칙이라 목록을 옮기는 것만으로는 안 깨진다.

### 남은 병목 (작다 — 빈도가 이미 목표를 넘어 방치 중)

- `무시(화면 밖)` 1건 — 후보로 뽑혔는데 발동 시점에 화면 밖이었다.
- `무시(후보 없음)` 3건 — 보충권을 이미 쓴 세대의 `active 1` 구간. 세대당 2회로 늘리면 잡힌다.

### 그래서 아래 Step 1~8은?

**보류다.** 착수 조건은 하나뿐이다 — **기습이 "언제·어디서" 터질지를 저작으로 통제해야 할 때.**
빈도·경고 시간은 이미 해결됐으므로, 남은 이유는 그것뿐이다.

## ⚠ Step -1이 먼저다 — 이 문서 전체가 필요 없을 수 있다

**경고 1초 고정은 지금 구조에서 이미 된다.** 링은 이미 임팩트에서 역산해 뜨고(`Update`의
`Time.time >= impactTime - ringDuration`), 흔들리는 것은 `ringDuration = clamp(lead, min, max)` 하나뿐이다.

그리고 `lead`는 창 길이가 아니다 — **`start`가 아니라 `now`부터 잰다**:

```csharp
float standing = end - Mathf.Max(start, Time.time);   // 서 있는 구간
float lead     = impact - Time.time;                  // ← 대시 구간까지 포함
```

`HandleIdleWindow`는 패턴이 판정 대상이 되는 순간 발행되고, 그때 플레이어는 아직 대시 중일 수 있어
`start`가 미래다. 기존 실측 로그가 그걸 보여준다:

```
와인드업 0.30s vs 링 0.40s · 임팩트까지 1.21s     ← lead 1.21초 (1초 경고가 이미 가능했다)
와인드업 0.10s vs 링 0.40s · 임팩트까지 0.54s     ← lead 0.54초 (탈락)
```

**즉 `maxRingExposure` 0.8이 자르고 있었을 뿐이다.**

- [x] **-1-1. `minRingExposure` 0.4 → 1.0, `maxRingExposure` 0.8 → 1.0.** (코드 기본값 + `BattleScene` 직렬화값 양쪽)
      `clamp(lead, 1, 1) = 1.0` 고정. **자격 검사가 안전장치다** —
      `RequiredLead = max(와인드업, minRingExposure)`이고 `PickClipWithin`이 `RequiredLead > lead`를 걸러내므로
      **발동한 기습은 반드시 `lead >= 1.0`**이다. 약속한 시간보다 짧게 보이는 경우가 구조적으로 안 생긴다.
- [x] **-1-2. 한 곡 돌려 빈도를 측정했다.** (공백 평가 60회 · 발동 2회)

  **① 노출 1초 고정 — 검증됨.** 두 발동 모두 `링 1.00s`이고 `임팩트까지`가 1.10 / 1.11로 둘 다 1.0 초과.
  자격 검사(`RequiredLead >= minRingExposure`)가 안전장치로 작동해 **약속보다 짧게 보이는 경우가 안 나온다.**

  **② 병목은 "창 부족"이 아니라 "후보 없음"이다.** 리드 ≥1.09인 기회가 **8번** 있었는데:

  §11-6의 "사망 1 : 스폰 1"로 **새 적이 화면 밖에서 태어나 걸어 들어오는 중**이라
  `IsIdle`(이동 중) · 시야 판정 둘 다 실패한다. `clusterSize: 4` − 현재 상대 1 = 실질 후보 3명뿐이다.
  → **시간이 가장 많은 창이 하필 후보가 가장 적은 순간이다.**

## 왜 이 방향을 준비해 두는가

지금 기습은 **남는 시간을 빌려 쓴다.** 채보가 우연히 남긴 공백에 들어가는데 그 공백은 곡이 정하므로
0.5~2.1초로 4배 흔들린다. **흔들리는 그릇 안에서 일정한 시간을 보장하려니** 예측이 필요해졌고
(`docs/AmbushLookahead/`), 예측은 어긋남 처리·경합·추정치를 줄줄이 달고 왔다.

요구 두 개가 같은 원인을 공유한다 — **시간이 없어서** 와인드업이 뭉개졌다.
실측(`docs/EnemyAmbushDodge/Plan_EnemyAmbushDodge.md`):

```
기습 발동 — MediumAttk1 (트림 0.84s ×2.0) · 와인드업 0.30s vs 링 0.40s (⚠ 링이 먼저)
기습 발동 — Swipe_4To6 (트림 0.28s ×2.0) · 와인드업 0.10s vs 링 0.40s (⚠ 링이 먼저)
```

에셋이 `speed: 2`로 저작된 이유가 이것이다. 0.5초에 접근·와인드업·임팩트를 다 넣으려니 배속을 두 배로 올렸다.

> **바꾸는 것 한 줄: "남는 시간을 빌린다" → "자기 시간을 갖는다".**
> 기습 시각을 채보가 소유하면 예산이 **구조적으로** 보장되고, 예측이 통째로 필요 없어진다
> (곡 시작 전에 이미 알고 있으므로).

⚠ 다만 **Step -1이 같은 통찰의 훨씬 싼 구현**이다 — "시간을 저작한다"를 새 데이터가 아니라
**채보의 공백**으로 표현한다. 잃는 것은 *"여기서 기습이 터진다"를 정확히 정하는 능력* 하나뿐이고,
그건 쿨다운 + 확률로 대략 대체된다. 아래는 그 대략으로 부족할 때의 안이다.

## Step 0 — 착수 전 결정 (완료)

- [x] 0-1. **곡당 기습 밀도** — 2분 곡에 **5~8회**. 후보 탐지의 최소 간격이 여기서 나온다(≈12초).

- [x] 0-2. **회피는 구르기로 유지한다.** 바꿔도 얻는 게 거의 없다 — 계산을 뜯어보면 필요시간 1.6초의 내역이
      **경고가 1.0초, 구르기는 0.25초**다:
  ```
  ringExposure     1.00   ← 경고 (임팩트 이전)
  dodgeWindow      0.15   ← 임팩트 이후 입력 유예
  rollMoveDuration 0.25   ← 구르기 이동 예산   ← 여기가 구르기 몫 전부
  margin           0.20
                   ────
                   1.60
  ```
      ⚠ **구르기는 이미 두 번 줄여져 있다**: 클립 0.8초를 `rollSpeed` 1.6으로 **0.5초로 압축**하고,
      그 0.5초조차 창에 요구하지 않고 **이동 최소치 0.25초만** 요구한다(`ResolveMoveDuration`의 근거 —
      클립 전체를 요구하면 발동 구간이 25% → 4%로 떨어진다).
      배속을 더 올려도 1.6 → 1.5 수준이고, 구르기가 더 빨라 보여 **"자연스러운 액션" 요구와 부딪힌다.**
      **초안의 "가벼운 스텝이면 1.2초"는 근거 없는 숫자였다 — 폐기.**
      → 오히려 저작 슬롯에서는 구르기가 **더 좋아진다**: 1.6초짜리 슬롯이면 `ResolveMoveDuration`이
      이동을 0.25가 아니라 **0.5초 전부**로 늘려 잡아, 짧은 공백에서 잘려 나가던 구르기가 온전히 보인다.
- [x] 0-3. **진짜 노브는 `ringExposure` 하나다** — 1.6초 중 1.0초가 그것이다.
      슬롯을 더 확보하려면 경고를 줄이는 수밖에 없는데 그게 이 작업의 요구 자체라 건드릴 대상이 아니다.

      다른 클래스가 `audioSource`를 만지기 시작하면 시계가 둘이 된다(§7-3 `timeScale` 함정과 같은 부류).
- [ ] 2-3. `preRoll`(기본 2.0초)은 **적이 준비할 시간**이다. `ringExposure`(1.0)보다 확실히 커야 한다 —
      그 차이가 곧 "걸어 나오고 자세 잡는" 구간이다.
- [ ] 2-4. `DodgeDirector.HandleAmbushScheduled(float impactTime)`:
  ```
  ① 후보 선정   PickIdleAmbusher (기존 그대로)
  ② 사전 접근   ScheduleApproach(마감 = impactTime - windup)
  ③ 클립 예약   AssignAttack(clip, impactTime, ...)   ← 시작 시점은 ClipAlignment가 역산
  ④ 링 예약     showTime = impactTime - ringExposure  ← 언제나 정확히 이 값
  ```
- [ ] 2-5. 후보가 없거나 전부 바쁘면 **그 슬롯은 조용히 넘긴다.** 저작된 슬롯이 반드시 터져야 하는 것은 아니다
      (Step 4-3의 확률 발동과 같은 처리 경로를 탄다).
- [ ] 2-6. 기존 게이트 중 **역할이 남는 것만** 옮긴다: 쿨다운, `CurrentAttacker == Enemy` 제외, 화면 안 판정.
      **없어지는 것**: 창 길이 검사, `lead` 계산, `RequiredLead`(Step 3-3).

## Step 3 — 링 노출 고정

- [ ] 3-1. `minRingExposure`/`maxRingExposure`를 **`ringExposure`(기본 1.0) 하나로 합친다.**
      요구가 "언제나 정확히"이므로 범위를 둘 이유가 없다. 값은 인스펙터에서 바꾼다.
- [ ] 3-2. `ringDuration`은 상수가 된다 — `Mathf.Clamp(lead, min, max)`가 사라진다(`DodgeDirector.cs:282`).
- [ ] 3-3. `RequiredLead`(`:328`)를 **제거한다.** 그 함수는 "이 클립이 남은 리드에 들어가는가"를 물었는데,
      이제 리드가 `preRoll`로 고정이라 물을 것이 없다. 클립 선별은 **와인드업이 `ringExposure`를 채우는가**로
      성격이 바뀐다(자연스러움 기준이지 가능/불가능 기준이 아니다).
- [ ] 3-4. ⚠ **`ringExposure`를 올려도 발동 빈도가 안 깎여야 한다.** 지금은 그 값이 발동 자격에 들어가 있어
      올리면 빈도가 직접 깎였다(`docs/AmbushLookahead/Research` §1-2). 이 Step 뒤로는 **저작이 빈도를 정한다.**

## Step 4 — 남는 위험

- [ ] 4-1. **`TakeTargetForWindow` 경합은 그대로 남는다.** 적을 고르는 곳이 둘인데 서로를 안 본다:
      `PickIdleAmbusher`는 `IsIdle`을 보지만(`EnemyDirector.cs:469`),
      상대 배정은 무리 소속과 **거리만** 본다(`:925~947`). 기습자는 `stageDistance`(2.5m)에 서 있어
      짧은 창에서 오히려 잘 뽑힌다.
- [ ] 4-2. `EnemyView`에 좁은 읽기면 하나(`HasPendingAction` = `hasPendingAttack || hasPendingReaction`)를 열고
      `TakeTargetForWindow`의 후보 루프에서 `continue`한다.
      ⚠ **`BusyReasonBy(t) != null`로 넓게 막으면 안 된다** — *이동 중*인 적까지 빠져
      무리 집결·링 복귀·등장이 상시 일어나는 §11-6에서 표적 선택이 좁아진다.
- [ ] 4-3. **랜덤성은 확률로 준다** — `ambushChance`(0~1). 슬롯은 저작하되 매번 터지지 않는다.
      매번 같은 자리면 예측 가능해져 긴장이 죽는다. **예산은 보장되고 놀람은 남는다.**
- [ ] 4-4. 쿨다운은 **안전장치로만** 남긴다(저작 밀도가 주 통제 수단이 된다).

## Step 5 — 굽기 툴

**이 Step이 이 안의 핵심이다.** 저작 부담을 여기서 없앤다.

- [ ] 5-1. `Tools/Pattern Chart Tool`(`PatternChartWindow`)에 **기습 레인**을 추가한다 — 타임라인 위 별도 줄.
- [ ] 5-2. **공백을 곡 전체에 대해 오프라인으로 계산한다.** 예보 설계에서 제일 헐거웠던 부분이
      여기서는 문제가 안 된다 — 값이 전부 정적이기 때문:
  ```
  공백 끝   = alignment.ResolveScheduleStart(deadline + ImpactOffset - TotalFreeze(perStop), firstNodeTime)
  공백 시작 ≈ 이전 패턴의 임팩트 + recoveryHoldDuration
  ```
      ⚠ **`ClipAlignment`의 기존 메서드를 그대로 부른다**(`:131` · `:88`). 새 수학을 만들면
      `CharacterActionPlayer.cs:709`와 두 벌이 된다.
- [ ] 5-3. ⚠ **공백 시작은 여기서도 추정치다**(`convergeUntil`은 런타임 값). 하지만 **성격이 다르다** —
      예보에서는 그 오차가 **경고 시간을 흔들었지만**, 여기서는 경고가 저작된 절대시각에 고정돼 있어
      오차는 "구르기가 들어가는가"에만 영향을 준다. 게다가 **사람이 여유를 보고 판단한다.**
- [ ] 5-4. `필요시간 = ringExposure + dodgeWindow + rollMoveDuration + margin`(기본값 기준 **1.6초**)보다
      긴 공백을 **후보로 자동 표시**한다. 저자는 취사선택만 한다.
- [ ] 5-5. 툴이 경고할 것: ① 공백보다 긴 슬롯 ② 다른 슬롯과 **12초 미만**으로 붙은 슬롯(0-1의 밀도 기준)
      ③ `Attacker.Enemy` 패턴과 겹치는 슬롯(적이 이미 휘두르는 중이다).
- [ ] 5-6. 저장은 기존 규율을 따른다 — 값이 이상하면 **몇 번째 슬롯인지 찍고 저장을 중단**한다
      (`spawnTimes` 재계산의 그 규율).

## Step 7 — 액션 다듬기 (시간이 생긴 뒤에야 가능한 것)

- [ ] 7-2. `preRoll`(2.0초) 구간에 **걸어 나오는 이동**이 보이게 한다 — `ScheduleApproach`의 마감을

- [ ] 7-3. ⚠ **링과 클립을 억지로 맞추지 않는다.** 각자 자기 시각에 자기 임팩트를 맞춘다(§6의 두 배우 규칙).

## 범위 밖

- **회피 동작 경량화**(구르기 → 스텝) — Step 0-2에서 **기각**. 얻는 게 0.1~0.15초뿐이고
  자연스러움을 잃는다. 구르기가 이 게임의 회피 정체성이라는 판단과도 맞다.
- **기존 채보 자동 채우기** — 후보 탐지(5-4)가 있으면 손으로 몇 분이면 된다. 자동 확정은 저작 의도를 뺏는다.
- **기습 전용 적 종류** — `EnemyDefinition.AmbushAttacks`가 이미 종류별 클립을 들고 있다. 그 이상은 나중에.
- **슬롯별 난이도 조절**(어떤 슬롯은 경고를 짧게) — 요구가 "일정한 시간"이라 정면으로 충돌한다.
  필요해지면 그때 `ringExposure`를 슬롯 단위로 내리는 확장을 검토한다(1-3의 구조체 승격 자리).
