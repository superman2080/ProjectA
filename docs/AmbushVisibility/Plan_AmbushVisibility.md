# Plan — 기습 가시성 (AmbushVisibility)

근거: `docs/AmbushVisibility/Research_AmbushVisibility.md`
범위: **A(소리) · B′(닷지 포인트 우하단 고정) · F(기습자 아웃라인) · E(노출 시간)**.

> **⚠ 방향 전환(2026-08-11).** 기존 B(화면 밖 지시자)와 겹침 구분(Step 3)은 폐기했다.
> 둘 다 "닷지 포인트가 적을 따라다닌다"를 전제로 한 대책인데, **그 전제 자체를 버리는 쪽이 싸다.**
> - 링을 **화면 구석에 고정**하면 화면 밖 문제도(B), 패턴 링과의 겹침 문제도(Step 3) **동시에 원천 소멸**한다.
>   `DodgePointView`의 코드 대부분이 월드→화면 투영이라 **줄어드는 변경**이다.
> - 대신 링이 못 주게 되는 "어디서 오는가"를 **기습자 아웃라인**(구 F)이 맡는다.
> - 역할이 깨끗하게 갈린다 — **아웃라인 = 누가·어디서 / 링 = 지금.**
>   지금은 링 하나가 둘을 겸하다가 **둘 다 애매하게** 하고 있다(자리는 적이 정하는데 화면 밖이면 사라지고,
>   중앙에 오면 패턴 링과 겹친다).

## Step 2 — B′: 닷지 포인트를 우하단에 고정

**이 Step은 코드를 지운다.** `DodgePointView`가 하는 일의 대부분(월드→화면 투영, 카메라 뒤 반전 처리,
`LateUpdate` 규율, 앵글 교체 대응)이 "적을 따라간다" 하나를 위해 있었다. 따라가지 않으면 전부 필요 없다.

- [x] 2-1. `DodgePointView`에서 추종 경로를 제거한다 — `follow`/`worldOffset`/`worldCamera`/`canvasRect`/
      `canvasCamera`, `UpdatePosition`, `LateUpdate`, 카메라 뒤 판정. `Show(Transform, Vector3, float)`는
      **`Show(float duration)`** 하나로 줄어든다.
- [x] 2-2. 자리는 **코드가 정한다** — `RectTransform`을 **우하단 앵커(1,0)**에 두고
      `pointMargin`(가장자리 여백, px) 하나만 노브로 남긴다. 4K 캔버스 기준 기본 (320, 320).
      ⚠ **패턴인풋 Point_3이 (700,-700)**이라 그 아래·오른쪽으로 확실히 벗어나야 한다(§패턴인풋 배치 좌표).
      ⚠ 씬에서 이 오브젝트는 `PatternHandler`(1400x1400)의 자식이었다 — 그 rect 기준으로 구석에 앵커하면
      캔버스 좌표로는 **패턴 영역 한가운데**가 된다. **`Canvas` 직속으로 옮겼다**(마지막 자식 = 맨 위 렌더).
- [x] 2-3. `SetVisible`은 **남긴다** — 배율(`pointScale`)의 유일한 지점이라는 이유는 그대로다.
      다만 "카메라 뒤라서 숨긴다"는 호출자가 사라지므로 `Show`/`Hide`만 쓴다.
- [x] 2-4. ⚠ **링 수축은 그대로다.** 링 소유·풀 반납·`ringColor`·`ringStartScale` 규율 전부 불변 —
      이 Step은 **자리만** 바꾼다. `endSize`를 못 만지는 이유(패턴 링과 같은 프리팹·같은 풀)도 그대로다.
- [x] 2-5. `DodgeDirector.ShowDodgePoint()`가 `ambusher.transform`·`promptHeight`를 넘기지 않게 된다.
      **`promptHeight` 필드는 제거한다**(다른 참조 없음 — 아웃라인은 높이를 안 쓴다).
- [x] 2-6. **C안(발동 시점 재확인)은 여전히 안 한다.** 링이 항상 같은 자리에 뜨므로 화면 밖 개념 자체가 없다.
- [x] 2-7. 겹침 구분(구 Step 3)은 **통째로 불필요**해진다 — 우하단은 패턴인풋 영역 밖이라 겹칠 수가 없다.
      `ringColor`를 패턴 팔레트와 다르게 두는 것만 관례로 유지한다(같은 자리에 안 뜨지만 "다른 입력"이라는 신호는 싸다).

## Step 3 — F: 기습자 아웃라인

"누가·어디서"를 여기가 전담한다. **새 셰이더를 쓰지 않는다** — 프로젝트에 이미 URP `RenderObjects`
아웃라인 인프라가 있다(`Assets/Shaders/CelOutline.shader`, `Assets/Shaders/Materials/CelOutlineMaterial.mat`,
`Assets/Shaders/Editor/AddOutlineRendererFeature.cs`).

- [x] 3-1. ⚠ **먼저 기존 피처의 실태를 확인한다.** `PC_Renderer.asset`의 `CharacterOutline`은
      `LayerMask.m_Bits = 256`(레이어 8)인데 **`TagManager.asset`의 레이어 8은 `SlicePiece`다.**
      에디터 스크립트 주석의 "Layer 8 = Character"는 사실과 다르다 — 즉 이 피처는 지금 캐릭터가 아니라
      **베인 조각에 걸려 있다.** 기습 아웃라인을 붙이기 전에 이걸 정리하지 않으면 원인을 두 개 들고 디버깅하게 된다.
- [x] 3-2. 빈 레이어 하나를 `AmbushOutline`으로 이름 붙인다(TagManager 9~31이 전부 비어 있다).
- [x] 3-3. `PC_Renderer`에 `RenderObjects` 피처를 **하나 더** 추가한다 — 그 레이어만 필터,
      `Event = AfterRenderingOpaques`, 경고색 아웃라인 머티리얼(`AmbushOutlineMaterial` — `CelOutlineMaterial`
      복제 후 색·두께만 변경). ⚠ 기존 `CharacterOutline`을 재사용하지 않는다 — 상시 아웃라인과 기습 경고는
      **보이는 이유가 다르다.**
- [x] 3-3-1. ⚠ **깊이 상태를 건드리면 안 된다**(`overrideDepthState = false`). 실패해 본 것을 남긴다 —
      "가려져도 비쳐 보이게" 하려고 `depthCompareFunction = Always`로 열었더니 **적 표면 전체가 칠해졌다.**
      `CelOutline`은 메쉬를 부풀린 뒤 **뒷면만**(`Cull Front`) 그리는 셸 방식이라 셸이 원래 앞면보다 뒤에 있고,
      **깊이 테스트가 그 겹치는 부분을 잘라내야 가장자리만 남는다.** 깊이를 열면 셸이 앞면 위에 통째로 그려진다.
      벽 너머 투시가 정말 필요하면 스텐실로 안쪽을 파내야 하는데, 기습 후보는 이미 **화면 안 판정**을 통과하므로
      (`DodgeDirector.IsVisible`) 가려지는 경우 자체가 드물다 — 살 값이 아니다.
- [x] 3-4. 켜고 끄는 것은 **뷰가 한다** — `EnemyView.SetHighlight(bool)`.
      근거는 기존 규율과 같다(§7-3 "배속은 뷰가, 시각은 디렉터가"): 렌더러 목록(`renderers`)과
      풀 반납 복구(`ResetState`)를 이미 뷰가 들고 있다.
- [x] 3-5. ⚠ **원래 레이어를 기억했다가 되돌린다.** 켤 때 서브트리 레이어를 스왑하고,
      끌 때 원복. 스왑 전 값은 **뷰가 필드로 하나** 든다(적 프리팹은 서브트리가 한 레이어다).
- [x] 3-6. ⚠ **`ResetState`에서 반드시 끈다.** 안 끄면 아웃라인이 켜진 채 풀에 반납되고
      **다음 대여가 빛나는 적으로 나온다**(기존 `dissolve`·`upperBodyWeight` 복구와 같은 부류의 함정).
- [x] 3-7. 배선 지점은 `DodgeDirector`의 **`Fire()`** — `cameraDirector?.SetAmbusher(ambusher)` 바로 옆이다.
      "공격하는 적이 확정된 순간"이 이미 거기라고 주석이 못박아 두었다. 끄는 곳은 `Finish()`와 **`Abort()` 양쪽**
      (기존 `ReleaseAmbusher`가 두 곳에 있는 것과 같은 이유).
- [x] 3-8. **아웃라인 자체가 경고다** — 별도 경고 표시를 앞에 세우지 않는다.
      `Fire()`가 곧 텔레그래프 시작(적 클립이 걸리는 순간)이라 시각이 이미 맞다. 소리(Step 1-3)도 같은 지점이다.
- [x] 3-9. 씬 카메라들의 **컬링 마스크에 새 레이어가 포함**되는지 확인(앵글 vcam 전부 — §7-5).
      빠지면 그 앵글에서만 적이 통째로 사라진다.
- [x] 3-10. `Attacker.Enemy`의 일반 공격에는 **안 건다.** 이 Step의 대상은 기습 하나다 —
      상시로 켜면 "특별한 사건"이라는 신호가 소모된다.

## Step 4 — E: 노출 시간 (⚠ 폐기 — 2026-08-12)

> `maxRingExposure`를 0.8 → 1.0으로 올리자는 안이었는데, **두 값을 1.0으로 맞춰 노출을 상수로 고정**하는
> 쪽으로 대체됐다(`docs/AmbushSlot/Plan_AmbushSlot.md`의 "결과" 절). 아래 4-1의 "min은 건드리지 마라"는
> **그때는 옳았고 지금은 전제가 바뀌었다** — 빈도는 후보 선정(`ReinforceActiveIfThin` 등)이 되찾았다.
> 4-2(시작 크기는 안 올린다)는 여전히 유효하다.

- [ ] 4-1. `maxRingExposure` 0.8 → **1.0**으로 올린다. `minRingExposure`는 **건드리지 않는다.**
      ⚠ 근거: `RequiredLead = max(와인드업, minRingExposure)`라 **min을 올리면 발동 빈도가 직접 깎인다**
      (공백 ≥0.8초가 25%뿐). max는 "여유가 있을 때 더 오래 보여준다"라서 빈도에 영향이 없다.
- [ ] 4-2. **시작 크기(`ringStartScale`)는 올리지 않는다.** 크기를 키우면 "크기 = 남은 시간" 학습이 깨진다 —
      노출이 길어지면 **수축이 느려질 뿐**이어야 한다(기존 툴팁의 규율).
- [ ] 4-3. A·B′·F를 먼저 넣고 **그다음에** 이 값을 만진다. 소리와 아웃라인이 들어가면 시간을 늘릴 필요가 없을 수 있다.

## 범위 밖

- **D. 중앙 신호(비네트·테두리 펄스)** — A·B′·F·E를 넣고 실제로 보고 판단한다.
  방향은 F(아웃라인)가, "지금 온다"는 D가 맡는 분업이라 둘은 배타적이지 않다.
- **아웃라인의 펄스·점멸** — 우선 상시 켬으로 넣는다. 시간 정보는 링이 이미 전담하므로(역할 분리)
  아웃라인까지 시간을 말하면 단서가 둘로 갈린다.
- **폐기: B(화면 밖 지시자) · 겹침 구분** — 문서 상단의 방향 전환 참조. 링이 고정되면 둘 다 존재하지 않는 문제다.
- **기습 빈도·난이도** — 이 문서는 "보이느냐"만 다룬다.
