## 1. 캐릭터 액션 복귀 블렌딩 (ReleaseRecovery)

### 1-1. 개정 1 — 복귀를 두 경로로 분리 (`b188391`, 7/22)

문제: 트림 끝(`actionEndTime`)에서 0.08초 급페이드로 Attack Layer 웨이트를 내려버려, 마무리 동작이 잘리고 콤보 사이에 Run이 비집고 들어왔다.

해결:
- **연계 있음(콤보)** — Attack Layer 웨이트를 **1로 유지**한 채 다음 클립으로 크로스페이드(0.05 → 0.15초). 레이어를 내렸다 올리지 않으므로 Run이 새어나오지 않는다.
- **연계 없음** — `recoveryHoldDuration` 동안 마무리 동작을 노출한 뒤 blend-out으로 Run과 크로스블렌드.
- 연계 판정은 기존 예약 정보(`pendingScheduleStart`)를 재사용해 새 상태를 만들지 않았다.
- 임계값 `comboLinkWindow = 1.0초`는 **채보 실측 분포에서 도출** — `Dreamer_lv10` 연결 111개 중 95%가 1.0초 이내, 절벽이 0.9↔1.2 사이.
- `actionEndTime`에서 `AttackSpeed`를 1로 복원 → 마무리 동작이 배속으로 지나가지 않게 함.
- 진입 측 팝핑 방지를 위해 레이어 웨이트를 blend-in으로 상승(`layerBlendInDuration`).
- 공격 클립에 tail이 없어 Release로 흘러가는 경우 Release가 재생 도중 잘리던 문제 수정 — `ReleaseSpeed` 파라미터 추가, `releaseDuration`(목표 재생 시간)에서 배속 역산해 완주시킨 뒤 Run으로 페이드.
- Release 오탐 주의사항 확인: CrossFade로 빠져나가는 중에도 현재 스테이트가 Release로 보인다 → 공격 스테이트 진입을 관측한 뒤부터만 인정하도록 가드.

Plan 진행: Step 1~7, 9~11 완료 / Step 8(MCP 실측) 자동 검증만 완료, 육안·미스 케이스는 사용자 확인 대기.

### 1-2. Release 지연 재생 버그 수정 (`968d271`, 7/22)

증상: 트림 끝과 클립 끝이 다른 클립(9개 중 8개)에서 Release가 **뒤늦게 튀어나옴**.

원인 두 가지를 분리해 규명:
1. **애니메이터** — Attack→Release 전이가 ExitTime 기반이라 클립 **전체**가 끝나야 발동. 트림 끝 이후 tail이 1.1~3.2초 남아 그만큼 지연.
2. **코드 회귀** — `UpdateReleaseState()`가 스테이트를 폴링해 "Release 재생 중이면 웨이트 유지"를 했는데, 그 시점엔 이미 blend-out이 끝나 Run이 나오는 중이었다. `ApplyBlendIn()`의 `blendInStartTime`이 과거라 보간이 즉시 완료되며 웨이트가 1로 튀어 Release가 갑자기 등장.

수정:
- 스테이트 폴링 제거. 트림 끝에서 **직접 `CrossFadeInFixedTime`으로 Release 진입**.
- 재생 시간이 `releaseDuration`으로 고정되므로 종료 시각도 시간 계산으로 확정(`releaseEndTime = 트리거 시각 + releaseDuration`).
- 추가: `releaseClip`(길이를 읽어 배속 역산), `releaseCrossFadeDuration`.
- 제거: `UpdateReleaseState()`, `releaseSpeedApplied`, `attackStateObserved`, `hasPlayedAction`.
- `recoveryHoldDuration` 의미 변경 — "Release로 넘어가기 전 **클립 자체의 tail**을 노출할 시간". 씬 값은 0(트림 끝 즉시 Release).
- 씬: `releaseClip` 배선, `recoveryHoldDuration = 0`.

교훈(문서화됨): **전이 중에는 현재/다음 스테이트가 뒤바뀌어 폴링 오탐이 잦다 → 시간 계산으로 확정하는 편이 안전하다.**

### 1-4. 개정 3 — 경로별 로코모션 분리 (`2545365`, 7/25)

  - 캐시: `runningLayerIndex`, `runStateHash`, `sprintStateHash`, `currentBaseStateHash`(중복 CrossFade 방지).

- **Step 23 — 실측으로 발견한 판별 버그 수정**: 처음엔 `releaseTriggered`로 갈랐으나, 콤보 gap도 **시작 순간 Release를 트리거**한다(`hasPending`이 뒤늦게 섬)는 사실이 로그로 드러났다. → 판별 기준을 **`releaseCompleted`(Release가 `releaseEndTime`까지 완주했는가)**로 교체. 완주=진짜 곡 공백→Run, 인터럽트=콤보 gap→Sprint. `releaseCompleted`는 다음 `PlaySlot`에서 리셋.
- 튜너블 조정: `blendOutDuration` 0.30 → 0.15, `layerBlendInDuration` 0.08 → 0.12.
- 최종적으로 복귀는 **세 경로**로 정리됨(세 경로 공통으로 `recoveryHoldDuration` 동안 마무리 동작을 웨이트 1로 노출한 뒤 분기):

  - ③ 연계 X(곡 공백) → Release를 압축 완주시킨 뒤 **Run**으로 페이드
- Step 22 실측 검증: 플레이 확인 완료. Step 18~23 전부 완료.

### 2-2. 검집 허리 고정(pelvis follow) 옵션 추가 (`7cb15d9`, 7/26)

문제: 검집 굽기를 끄면 `add_weapon_l`에 커브가 아예 없어, root 직계 자식인 검집이 **바인드 포즈 한 점에 얼어붙어** 몸을 따라가지 않았다.

해결:
- `SheathMode` enum 도입(`None` / `Waist` / `Hand`), 윈도우 UI를 체크박스에서 **3단계 드롭다운**으로 교체.
- `Waist` 모드: 샘플링 전 신선한 인스턴스의 바인드 포즈에서 **pelvis 기준 오프셋을 1회 캡처**(`CaptureBindOffset`)한 뒤, 프레임마다 강체로 복원 → 허리 위치를 유지한 채 몸의 회전·이동을 따라간다. **참조 클립이 필요 없다.**
- `pelvis` 본 해석 추가. 참조 클립은 칼/손그립 모드일 때만 요구하도록 버튼 활성 조건 조정.
- `Flurry_Slashes`에 허리 고정으로 굽기 적용(기존 칼 커브 7개 보존 + `add_weapon_l` 커브 7개(pos3 + rot4) 신규 기입 확인).
- 실측값: 검집 오프셋 pelvis 기준 `(0.0061, 0.1710, 0.5305)`, 회전 편차 0.00도. Z 0.53m는 기존 실측 "허리에서 52cm 옆"과 일치.

Plan 진행: S1~S5 완료 / S6은 데이터 검증 통과, **육안 검증(몸 회전 시 검집이 허리를 따라 도는지)과 나머지 두 클립 처리 여부는 사용자 확인 대기**.

## 4. 신규 시스템 설계 착수 — 베이는 표적 (SliceTarget)

문서(미커밋): `docs/SliceTarget/Research_SliceTarget.md`(7/26 19:58), `docs/SliceTarget/Plan_SliceTarget.md`(7/26 20:00)

칼 모션에 맞춰 표적이 다가오고, 패턴 성공 시 **미리 구운 조각으로 갈라 흩뿌리는** 연출 시스템의 Research/Plan을 작성했다(구현 전, 파이프라인 2단계까지 진행).

브레인스토밍으로 확정한 사항:

| 항목 | 결정 |
|---|---|
| 표적의 성격 | 순수 연출용 — 판정/점수에 영향 없음 |
| 분할 방식 | 런타임 메쉬 컷이 아니라 **에디터에서 미리 버텍스 단위로 절단해 구운 조각 프리팹 교체** |
| 조각 수 | **2조각이라 가정하지 않는다** — 조각 N개, 단면 폐루프 다수를 1급 전제로 |
| 지정 방식 | `Pattern`이 enum(`SliceObjectType`, `SliceShape`)으로 지정 → 카탈로그가 실물 프리팹 소유 |
| SliceShape | `Horizontal / Vertical / Diagonal / Cross / Dice` 5종 |
| 절단 시각 | 마지막 노드 판정 시각(`ActivePattern.LastNodeTime`) |
| 등장 | 고정 접근시간 역산 — 스폰 = 임팩트 − `approachDuration`, −Z 등속 이동 |
| 흩뿌림 | Z 속도 유지, **X·Y만** 플레이어 반대 방향 임펄스 |
| 실패(미스) | 관통 금지 — 플레이어와 충돌 후 이펙트와 함께 소멸 |

Research에서 규명한 **핵심 제약**: 기존 이벤트로는 표적 스폰 훅을 만들 수 없다. `OnJudgeTargetBegan`은 직전 패턴이 끝난 뒤에야 발화해 남은 시간이 0.4~1.5초뿐이라 접근시간(≈1.5초)을 확보하지 못한다. → **`SetPattern` 시점에 발화하는 `OnPatternQueued` 이벤트 1개 추가**가 필요하다는 결론(채보의 95%가 겹치므로 큐 투입은 판정 시작보다 확실히 앞선다). `PatternHandler`는 이 이벤트 추가 외에는 수정하지 않는다(`EffectManager` 선례의 관심사 분리 원칙 유지).

Plan 아키텍처 요약:
```
[에디터]  MeshSliceBakerWindow → MeshSliceBaker(순수 기하) → SliceSet(SO) → SliceCatalog(SO)
[런타임]  Pattern.sliceTargets(SliceSpec[])
          OnPatternQueued(신규) ┐
          OnPatternComplete     ├→ SliceTargetDirector → SliceTargetView(−Z 등속)
          OnJudgeTargetFirstMiss┘        성공: 조각 교체 + XY 임펄스 / 실패: 충돌 이펙트 + 소멸
```
