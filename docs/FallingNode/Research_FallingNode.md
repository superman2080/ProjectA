# Research_FallingNode.md — 패턴 노드 역할(시작/진행/끝) 및 낙하 노드 시스템

## 목적
현재 `Pattern`(SO)은 `PatternData[]`(인덱스 + 입력 타이밍)만으로 구성되어, "언제 어떤 인덱스를 눌러야 하는가"라는 추상적 타이밍 판정만 수행한다. 리듬게임 본연의 "노드가 위에서 떨어지고, 플레이어가 그 시점에 맞춰 드래그로 훑어 처리한다"는 시각적 낙하 요소는 아직 존재하지 않는다.

이번 설계 목표: 패턴을 구성하는 각 노드에 **역할(시작/진행/끝)** 개념을 부여하고, 해당 역할에 따라 노드가 3x3 패턴인풋 위로 떨어지는 형태로 스폰되어, 플레이어가 시작 노드부터 끝 노드까지 드래그로 이어 처리하면 해당 패턴이 완료되도록 한다.

## 관련 코드 분석

### `Pattern.cs` (`Assets/02. Scripts/Pattern/Pattern.cs`)
- `PatternData { int index (0~8), float inputTime }` 의 배열을 `patternDatas`로 보유하는 ScriptableObject.
- `Initialize()` — `index = 0`, `nowPattern = patternDatas[0]`으로 리셋.
- `Input()` — `OnInput` 이벤트 발행 후 `Next()`로 진행.
- `Next()` — 마지막 데이터가 아니면 다음 `PatternData`로 이동, 마지막이면 `OnExit` 이벤트 발행.
- **현재 "시작/진행/끝" 구분이 전혀 없음** — 배열의 첫 원소가 암묵적 시작, 마지막 원소가 암묵적 끝일 뿐 명시적 타입 필드가 없다.
- 패턴 하나당 `nowPattern` 단일 상태만 가지므로, **동시에 여러 패턴 인스턴스가 진행 중인 상황(여러 낙하 노드가 겹쳐 존재)을 표현할 수 없다.**

### `PatternHandler.cs` (`Assets/02. Scripts/UI/PatternHandler.cs`)
- `SetPattern(Pattern pattern)` — 현재 재생 중인 패턴을 **하나만** 교체하는 구조 (`nowPattern` 필드가 단일).
- `AddPattern(int index)` — 드래그/키보드로 눌린 인덱스가 `nowPattern.ExpectedPointIndex`와 일치하는지, 그리고 `patternStartTime + ExpectedTime` 대비 `Time.time` 오차로 Perfect/Good/Miss를 판정.
  - 이 판정은 **패턴 시작 시각(`patternStartTime`) 기준 절대 시간**으로 계산되며, 실제로 노드가 화면 위에서 "떨어지는" 움직임과는 아직 연결되어 있지 않다. 즉 지금은 시각적 낙하 없이 타이밍만 판정하는 상태.
- `HandlePatternComplete()` — `Pattern.OnExit` 구독, 패턴 종료 시 `OnPatternComplete` 발행 후 `nowPattern = null`.
- 패턴 완료/실패 판정은 전부 **인덱스 단위**로 이뤄지고, 인덱스가 "시작/진행/끝" 중 무엇인지에 따라 분기하는 로직은 없음.
- `OnPointPressed(int index)`가 통과 노드 자동 인식(`GetPassThroughIndex`) 로직까지 포함해 매 노드 진입마다 `AddPattern(index)`를 호출 — 이 흐름 자체는 "끝 노드에 도달했는지" 검사를 끼워 넣기에 적합한 지점.

### `Point.cs`
- 노드 자체는 역할(시작/진행/끝)에 대한 정보를 전혀 갖지 않는 순수 입력 컴포넌트(`IPointerDownHandler` 등). 노드 오브젝트는 3x3 그리드에 고정 배치된 UI 오브젝트이며, "낙하하는 노드"라는 별도 오브젝트 개념은 없음.
- `ForceDown()` — 통과 노드 자동 인식 시 실제 포인터 이벤트 없이 강제로 Down 처리하는 훅. 낙하 노드가 스폰/디스폰되는 시점과는 무관.

### `JudgementResult.cs`
- `Perfect / Good / Miss` 3단계 열거형. 낙하 노드의 "도착 판정선(Judge Line)" 개념과 연결될 수 있는 유일한 기존 개념.

### `PatternLineRenderer.cs`
- 드래그 궤적을 그리는 시각 컴포넌트. 낙하 노드 자체의 시각화(스폰 위치, 낙하 애니메이션, 판정선 도달 등)와는 무관하며 재사용 대상이 아님.

## 현재 구조의 한계 (이번 설계에서 다뤄야 할 공백)

1. **역할 필드 부재**: `PatternData`에 시작/진행/끝을 나타내는 필드가 없다. 지금은 배열 순서(`index == 0` → 시작, 마지막 원소 → 끝)로만 암묵적으로 구분 가능.
2. **낙하 시각 요소 부재**: "노드가 위에서 떨어진다"는 게임 컨셉(CLAUDE.md 게임 개요)에 대응하는 실제 오브젝트/애니메이션이 코드에 없다. 지금의 `PatternHandler`는 순수 타이밍 계산기이고, 3x3 그리드의 `Point` 9개는 고정된 입력 수신기일 뿐이다.
3. **단일 패턴 진행 가정**: `PatternHandler.nowPattern`이 단일 필드라 여러 `Pattern` SO(또는 그 낙하 인스턴스)가 동시에 화면에 떠 있는 상황을 표현하지 못한다. "패턴SO를 드래그해서 처리"라는 요구사항이 여러 패턴을 순차적으로만 처리하는 것인지, 동시에 여러 개를 처리하는 것인지에 따라 이 필드 구조를 확장해야 할 수 있다.
4. **끝 노드 도달 판정 지점**: `AddPattern(index)` 안에서 `nowPattern.Input()`을 호출한 뒤 내부적으로 `Next()`가 마지막 원소 여부를 판단해 `OnExit`을 발행하는 구조라, "끝 노드를 마주쳤을 때 패턴 종료"라는 요구사항 자체는 이미 이 이벤트 체인으로 충족되고 있다. 다만 명시적으로 "이 노드가 End 타입이라서 종료"가 아니라 "배열의 마지막이라서 종료"인 차이가 있다.

## 추가 리서치 (v8) — 낙하 연출을 "화면 바깥 상단에서 낙하"하는 표준 리듬게임 방식으로 재설계

### 지금까지의 시행착오와 왜 잘못됐는지
1. **v5~v6**: `FallingNodeParent`(작은 700×700 패널, `PointBackground`의 로컬 rect)의 `rect.yMax`(로컬 +350)를 "이 위는 안 보인다"는 경계로 가정하고, 그 경계 안쪽만 `visibleExposureDuration` 동안 이동하도록 **행마다 낙하 시간을 다르게 역산**했다. 문제는 그 경계가 실제로 아무것도 가리지 않는다는 것(아래 확인) — 그 결과 역산된 서로 다른 낙하 시간이 그대로 노출 시간이 되어버려 편차가 더 커졌다.
2. **v7(되돌림)**: `FallingNodeParent`에 `RectMask2D`를 추가해 그 경계를 실제로 가리도록 "땜질"했다. 하지만 이 방식은 **노드를 패널 안쪽의 작은 사각형 뒤에 숨기는 것**이라, 사용자가 원하는 "화면 바깥(실제 모니터/캔버스 바깥) 위쪽에서 떨어지는" 느낌과 다르다. 사용자가 명시적으로 거부(잘못된 방향) — **원복 완료**.

### 실제 씬의 화면/좌표 체계 (직접 확인한 값)
- `Canvas`(루트, `Screen Space - Overlay`): `RectTransform.rect`가 x: -1920~1920, y: -1080~1080 (3840×2160), `CanvasScaler.uiScaleMode = Constant Pixel Size`(스케일 없음). 즉 **Canvas의 rect 자체가 실제 화면 해상도와 정확히 일치**하며, Canvas 바깥은 실제로 렌더링되지 않는(하드웨어 뷰포트 클리핑) 진짜 "화면 밖"이다. 별도 Mask 없이도 Canvas 좌표계 밖으로 나가면 자연히 안 보인다.
- `TileArea`(Canvas 자식): 1920×2160, Canvas 전체 높이를 채움.
- `PointBackground`(패턴인풋 패널, `TileArea` 자식): 700×700, anchor 하단 중앙, `anchoredPosition (0, 400)` — 화면 하단부에 위치. 월드 좌표 `(2880, 400)`.
- `FallingNodeParent`(`PointBackground`의 자식, `PointBackground`와 동일 rect로 스트레치): 로컬 rect -350~+350, 월드 좌표는 `PointBackground`와 동일 `(2880, 400)`.
- **결론**: `FallingNodeParent` 로컬 좌표 기준으로 "진짜 화면 상단"은 `캔버스 상단 월드Y(2160) - FallingNodeParent 월드Y(400) = 로컬 Y 1760` 부근이다 (패널 자신의 rect 경계 +350과는 전혀 다른 값). 이 값도 패널이 화면 어디에 배치되느냐에 따라 달라지므로, **하드코딩하지 않고 런타임에 Canvas의 실제 rect로부터 계산**해야 한다.

### 일반적인 리듬게임의 낙하 노트 구현 방식 (참고)
낙하형 리듬게임(비트매니아/오사매니아/기타히어로 등)은 보통 다음과 같이 동작한다:
- 각 레인/노드는 **화면 상단 바깥의 고정된 스폰 지점**에서 시작해 **화면 하단의 판정선**까지 **일정한 속도(등속)**로 이동한다.
- "노출 시간"을 노트마다 다르게 맞추는 개념 자체가 없다 — 속도가 일정하므로 스폰 지점부터 판정선까지 거리가 길면 화면에 보이는 시간도 자연히 길고, 짧으면 짧다. 이 차이는 버그가 아니라 정상적인 리듬게임 특성이다.
- 스폰 시각은 항상 "판정 시각 - (거리 / 속도)"로 역산해서, 어떤 노트든 정확히 판정 시각에 판정선에 도달하도록 맞춘다.
- 이번 프로젝트는 3x3 그리드라 Point마다 목표 Y가 달라(하단/중단/상단 행), 스폰 지점(화면 상단 바깥의 고정 라인)부터 각 Point까지 거리가 행마다 다르다 — 이는 정상이며, 굳이 "노출 시간 동일화"를 할 필요가 없다. 오히려 **속도를 통일**하는 것이 표준적이고 자연스럽다.

### 이번 재설계에서 확정할 것
- "노출 시간 균일화"(v5~v7) 개념은 전부 폐기한다. 대신 **모든 노드가 동일한 낙하 속도(units/sec)로 이동**하는 표준 리듬게임 모델로 되돌린다.
- 스폰 위치는 여전히 절대 좌표(v6에서 도입한 `fallSpawnPositionY` 개념)를 유지하되, 값 자체는 하드코딩하지 않고 **Canvas의 실제 rect에서 계산한 "진짜 화면 상단보다 더 위"**로 설정해, Mask 없이도 자연스럽게 화면 밖에서 시작하도록 한다.
- Mask/RectMask2D는 사용하지 않는다.
