# Research — 점수 · 콤보 (ScoreCombo)

노트 판정별 배점 + 패턴 성공 보너스 + 콤보 보너스로 점수를 매긴다. 이 문서는 **"노트 하나의 성패"를 어디서 알 수 있는가**를 기존 이벤트에서 찾고, 그 과정에서 드러난 함정을 기록한다.

## 2. 노트 판정 이벤트의 실제 발행 경로

`PatternHandler.AddPattern`(`:584`)이 갈래를 셋으로 나눈다.

| 입력 | `OnJudged` | `Advance` | 비고 |
|---|---|---|---|
| **오답 인덱스** (`:590`) | X **안 난다** | X | `MarkIncorrect` + Miss 색만. 패턴이 정체한다 |
| 정답 + Perfect/Good | O | O | |
| 정답 + 타이밍 Miss (`:607`) | O `Miss` | O | 진행은 된다 |
| **아무 입력 없음** | X | X | 패턴이 `Deadline`에 만료될 때까지 그 노드는 판정되지 않는다 |

**즉 `OnJudged`만 세면 "친 노트"만 보이고 "놓친 노트"는 안 보인다.** 콤보를 끊어야 하는 사건의 절반이 이벤트로 오지 않는다.

---

## 3. ⚠ `OnFocusRingMissedArrival`은 "놓쳤다"가 아니다 (가장 중요한 발견)

이름만 보면 이것이 "안 친 노트"의 신호 같지만 **아니다.**

- 링의 `OnArrived`는 수축이 끝나는 순간, 곧 **`ExpectedTime` 정각**에 발행된다(`FocusRingView.cs:92`).
- `PatternHandler.HandleFocusRingArrived`(`:705`)가 그 자리에서 **즉시** `OnFocusRingMissedArrival`을 발행한다.
- 그런데 판정 창은 `ExpectedTime ± goodWindow`다. **정각보다 늦은 입력도 정상적인 Perfect/Good이다**(Perfect는 +0.05초까지, Good은 +0.1초까지).

→ **늦은 쪽 입력은 전부 `OnFocusRingMissedArrival`을 먼저 발행한 뒤 `OnJudged(Perfect/Good)`을 발행한다.** 산술적으로 판정 창의 절반이 여기 해당한다. 이 이벤트로 콤보를 끊으면 **정확히 친 노트의 절반이 콤보를 끊는다.**

이 이벤트는 원래 목적(링이 시각적으로 사라지는 순간의 연출)에는 맞지만 **채점의 입력으로는 못 쓴다.**

---

## 4. 그럼 "놓친 노트"를 어떻게 세는가 — 페이로드 뺄셈

`PatternCompletionInfo`가 `Template`을 들고 있고(`PatternCompletionInfo.cs:18`), 템플릿은 `AllData.Count`로 **이 패턴의 노드 수**를 안다.

```
그 패턴에서 놓친 노트 = Template.AllData.Count − (그 패턴에서 OnJudged가 난 횟수)
```

패턴은 **판정 대상이 언제나 선두 하나**(§3)이고 완료는 순차적이라, "지금 카운트 중인 패턴"이 애매해질 여지가 없다. `OnJudged` → 카운터 증가, `OnPatternComplete` → 차이만큼 Miss 처리 후 카운터 리셋.

**⚠ 이 방식의 이점: `PatternHandler`를 한 줄도 안 고친다.** §7의 "PatternHandler는 이펙트를 위해 수정하지 않는다(관심사 분리)" 규율이 그대로 유지된다.

**⚠ 오답 인덱스 연타는 자동으로 걸러진다.** `OnJudged`가 안 나므로 카운터가 안 오르고, 만료 시 뺄셈에 그대로 잡힌다. 다만 **오답 자체는 콤보를 안 끊는다** — 끊는 것은 그 결과로 놓치게 된 노트다. (오답 즉시 끊고 싶으면 `OnJudgeTargetFirstMiss`(`:594`)가 이미 있다.)

## 5. 총 노트 수는 곡 시작 전에 알 수 있다

`SongChart.entries[]`의 각 `SongChartEntry`가 `onsetTimes[]`(노드별 판정 시각)를 든다(`SongChart.cs:14`). 따라서:

```
총 노트 수   = Σ entries[i].onsetTimes.Length
총 패턴 수   = entries.Length
```

전부 **재생 전에 확정**된다 → 점수를 고정 만점으로 정규화할 수 있다(§7).

⚠ `ChartPlayer.ActiveChart`(`:38~42`, `GameSession.SelectedChart` 우선 · 없으면 `debugChart`)는 지금 **private**이다. 채점기가 같은 판단을 복제하지 않으려면 이것을 공개해야 한다 — 곡의 진실의 원천을 둘로 만들면 디버그 재생에서만 만점이 어긋난다.

## 7. 점수 모델의 갈림길 — 누적형 vs 정규화형

| | 누적형 | 정규화형(만점 고정) |
|---|---|---|
| 총점 | 곡 길이에 비례 | 언제나 같은 만점(예: 1,000,000) |
| 곡 간 비교 | 불가 | 가능 |
| 등급(S/A/B) | 기준을 곡마다 따로 | 만점 비율 하나로 |
| 필요한 것 | 없음 | 총 노트/패턴 수 (§5 — 이미 있다) |

리듬게임에서 등급·랭킹이 붙는 순간 정규화형이 사실상 필수이고, **필요한 사전 정보를 이미 다 갖고 있다.** 누적형으로 시작하면 나중에 정규화로 바꿀 때 저장된 기록이 전부 무의미해진다.

### 콤보 보너스를 '배율'로 걸면 안 되는 이유

노트 점수에 `combo × k`를 곱하면 **같은 Perfect라도 곡 후반이 몇 배 비싸진다.** 초반 실수 하나가 후반 실수 하나보다 훨씬 싸게 먹히고, 곡 끝에서만 집중하는 플레이가 유리해진다.

콤보를 **별도 배점 풀**로 두면 그 왜곡이 사라진다. 노트 하나가 기여하는 콤보 점수를 "그 시점의 콤보 수"로 잡으면:

```
콤보 점수 = Σ(각 노트 시점의 콤보 수) / (1 + 2 + ... + N) × 콤보 풀
          = Σ combo_i / (N(N+1)/2) × 콤보 풀
```

- 분모가 **풀콤보일 때의 값**이라 만점이 정확히 풀콤보에서 나온다
- 튜닝 테이블·구간 배율이 없다(닫힌 식)
- 긴 사슬이 짧은 사슬 여럿보다 유리하다는 성질이 자동으로 성립한다

## 8. HUD가 붙을 자리

루트 Canvas는 **`ScreenSpaceOverlay`, 3840x2160**이고 `PointBackground`가 화면 중앙(§1)이다. 패턴인풋은 중앙 ±700px을 쓰므로 점수·콤보는 그 밖(상단/모서리)에 둔다 — `DodgePointView`가 우하단 고정으로 같은 판단을 이미 내렸다(§11-8).

⚠ **콤보 표시가 패턴 링과 겹치면 안 된다.** Point_9가 (700, 700)이라 우상단은 여유가 있다.

## 9. 제약 정리

- 채점기는 **연출이 아니라 상태**다. 그래도 `PatternHandler`를 수정하지 않는다는 규율은 같다 — 이벤트만 구독한다.
- `Time.timeScale`을 쓰지 않으므로(§7-3) 히트스톱이 점수에 영향을 주지 않는다.
- 오토플레이(§8)는 `ForceDown` → 같은 파이프라인이라 **점수도 그대로 쌓인다**. 디버그로 만점을 만들 수 있다는 뜻 — 기록 저장이 붙으면 그때 막아야 한다.
- 결과 화면이 없다. 최종 점수를 어디에 두느냐(`GameSession`)만 정해 두고 화면은 범위 밖으로 둔다.
