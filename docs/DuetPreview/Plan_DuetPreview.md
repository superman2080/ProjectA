## 0. 왜 단위를 올리나

표적이 오브젝트였을 때는 **플레이어 모션과 베이는 프리뷰가 따로 있어도 충분**했다.
표적은 반응하지 않으니 각자 확인하면 됐다.

적이 인터랙티브해지면서 저작 단위가 **둘의 상호작용**으로 바뀌었다. 확인해야 하는 것:

- 칼이 적 몸에 실제로 닿는가, 앞뒤로 빗나가는가
- 임팩트 순간 적의 포즈가 베이기에 말이 되는가
- 패링이면 두 칼이 같은 지점에서 만나는가

**그런데 이 판단은 두 마크를 동시에 조정해야 수렴한다.** 슬롯을 하나씩 열어 찍고 나가서
다시 열어 찍는 방식으로는 되먹임이 안 된다.

→ 툴이 **패턴 하나를 열어 짝을 통째로 저작**하고, 저장도 한 번에 한다.

### 시간 정렬은 런타임 문제가 아니다 (거리는 다르다)

혼동하기 쉬워서 못박아 둔다 — **런타임 임팩트 정렬은 이미 동작한다.**

| 무엇 | 상태 |
|---|---|
| 런타임 임팩트 정렬 | **동작 중.** 배속 차이는 문제가 아니라 정렬을 맞추는 **수단**이다(`ResolvePlaySpeed`) |
| 정렬이 실제로 깨지는 유일한 경우 | 필요 배속이 `maxAttackSpeed`(2.5)를 넘을 때 = **리드타임 부족**. 런타임 경고가 잡는다 |
| **이 플랜이 푸는 것** | 저작자가 **둘이 만나는 그림을 볼 방법이 없다**(저작 가시성) |
| 결정 1-4의 "위험" | **앞으로 쓸 툴 코드**의 시간 단위 혼동. 런타임과 무관 |

**단, 결투 거리(결정 1-10)만은 런타임을 바꾼다.** 프리뷰에서만 거리를 조절하면
"툴에선 닿는데 게임에선 안 닿는" 거짓 확인이 된다 — 그럴 바엔 프리뷰를 안 만드는 게 낫다.

## 1. 설계 결정

### 1-1. 저작 단위는 **패턴 하나 = 배우 둘**
`Pattern`을 열면 `attacker`가 짝을 정한다(`PatternAttacker` 결과 재사용):

| `attacker` | 플레이어 배우 | 적 배우 |
|---|---|---|
| `Player` | `playerAttack` | `enemyDeath` |
| `Enemy` | `playerParry` | `enemyAttack` |

배우마다 **클립 + Start/Impact/End**를 각자 갖는다. 화면에 두 블록이 나란히 선다.

>>> (완료) 확정 (2026-08-01)

### 1-2. 시간축은 **임팩트 기준 상대시간 하나** (배속을 식에 포함한다)
클립마다 길이도 임팩트 위치도 배속도 다르므로 클립 시간으로는 나란히 놓을 수 없다.
런타임 정렬 규칙(`ClipAlignment`)을 그대로 옮긴다:

```
샘플 시각 = actor.ImpactTime + t × actor.Speed

t = 0  →  두 클립이 각자의 임팩트 프레임   ← 배속이 식에서 사라진다
```

`t = 0`이 곧 **칼이 지나가는 순간 = 적이 베어지는 순간**이다.
스크럽 범위는 두 트림 구간을 임팩트 기준 상대시간으로 환산해 겹친 합집합.

#### 배속이 달라도 이 프리뷰가 성립하는 이유

**배속은 정렬을 깨는 요인이 아니라 정렬을 맞추는 수단이다** —
런타임은 각 배우가 자기 임팩트를 공유 시각에 얹도록 배속을 따로 계산한다(`ResolvePlaySpeed`).
그래서 배속이 서로 달라도 임팩트 프레임은 같은 순간에 온다.

프리뷰에서 중요한 것은 그 결과다:

- **`t = 0`에서는 배속이 식에서 소거된다.** 저작자가 실제로 판단하는 것
  (칼이 닿나 / 두 칼이 만나나 / 적 포즈가 베이기에 말이 되나)은 **전부 여기서 결정되고 정확하다.**
- `t`가 0에서 멀어지면 런타임 압축과 어긋난다. 하지만 그 압축값은 채보 간격과 입력 시각마다
  달라 **재현할 대상 자체가 없다.** 결정하지 않는 구간이라 문제가 되지 않는다.

→ **결정하는 곳은 정확하고, 부정확한 곳은 결정하지 않는 곳이다.**

>>> (완료) 확정 (2026-08-01)

### 1-3. `Mark Impact`는 시간축의 원점을 옮긴다 (정확성이 아니라 **UX** 항목)
임팩트가 `t = 0`의 정의이므로, 어떤 배우의 임팩트를 옮기면 원점이 따라 옮겨진다.
누른 프레임이 곧 새 임팩트이므로 **`t`는 0이 된다** — 결정 1-4의 식에서 저절로 나오는 결과다
(`t = 지금클립시각 − 새임팩트 = 0`). 별도 보정 코드가 필요한 게 아니라,
**슬라이더 핸들이 0으로 이동하는 것을 확인만 하면 된다.**

`Mark Start` / `Mark End`는 트림 경계만 옮기므로 원점을 안 건드린다.

>>> (완료) 확정 (2026-08-01)

### 1-4. **상태는 클립 시간, `t`는 뷰 전용 파생값** (조용한 오차를 구조로 제거)

원안은 "저장할 때 상대시간 → 클립 시간으로 환산"이었다. **그건 변환을 저장 경로에 앉히는 것이고,
저장 경로의 오류는 화면에 안 나타나 조용하다.** 위험을 없애려면 변환을 저장 경로에서 빼내야 한다.

```
상태   actor.clipStart / clipImpact / clipEnd    ← 에셋과 같은 단위(클립 초)
뷰     t  →  샘플 시각 = actor.clipImpact + t    ← 파생. 저장하지 않는다
마킹   actor.clipStart = actor.clipImpact + t    ← 변환은 여기 한 곳
저장   에셋 ← 상태 그대로 복사                    ← 변환 0
```

얻는 것:

- **저장에 변환이 없다** — 틀릴 코드가 존재하지 않는다.
- 남은 변환은 **샘플링 한 곳**이고, 거기가 틀리면 **프리뷰가 즉시 이상해진다.** 조용하지 않다.
- `Mark Impact` 후 `t = 0`도 특수 처리가 아니라 식에서 저절로 나온다
  (`t = 지금클립시각 − 새임팩트 = 0`). 결정 1-3이 UX 편의로 격하된다.

**마크 입력 필드도 클립 시간으로 표시한다**(슬라이더만 상대시간).
저작자가 보는 숫자 = 에셋에 들어가는 숫자라, 인스펙터로 열어 대조하면 눈으로 검증된다.

>>> (완료) 확정 (2026-08-01)

### 1-5. 배치는 **결투 거리 하나**
플레이어는 원점에서 +Z, 적은 결투 거리 앞에서 마주 본다.
슬라이서 휴머노이드 모드와 **같은 규약·같은 값**을 쓴다 — 두 툴이 다른 그림을 보여주면 안 된다.
씬 참조는 끌어오지 않는다(프리팹만으로 확인 가능해야 한다).

>>> (완료) 확정 (2026-08-01)

### 1-10. 결투 거리는 **씬 기준선 + 패턴 보정**이다 (런타임 포함)

거리를 프리뷰 노브로만 두면 **"툴에선 닿는데 게임에선 안 닿는"** 거짓 확인이 된다.
모션마다 리치가 다르므로 거리도 저작 데이터여야 한다.

**절대 거리가 아니라 보정값으로 둔다:**

```
결투 위치 = duelAnchor(씬)  +  Pattern.duelDistanceOffset × (중앙→앵커 방향)
```

| 값 | 소유자 | 뜻 |
|---|---|---|
| 기준선 | 씬 `duelAnchor` | 카메라 구도에 맞춰 잡은 기본 간격 (가이드 4단계) |
| 보정 | `Pattern.duelDistanceOffset` (기본 **0**) | 이 모션의 리치에 맞춘 ± 조정 |

- **기본 0이라 기존 동작이 그대로다.** 마이그레이션이 필요 없다.
- 씬 튜닝(구도)과 패턴 저작(리치)이 **각자 자기 축을 갖는다** — 한쪽을 바꿔도 다른 쪽이 안 깨진다.
- 절대 거리로 두면 패턴마다 카메라 구도까지 흔들린다.

**소비자 전원이 같은 식을 쓴다** — 런타임(`EnemyDirector.DuelPosition`),
합주 프리뷰, 슬라이서 칼 평면 유도. 슬라이서가 다른 거리를 쓰면 **유도된 절단 평면 자체가 틀린다.**

툴은 씬을 못 읽으므로 **기준선을 수동 필드로** 노출하고 패턴 보정을 더한다
(가이드 4단계에서 잡은 값을 넣으라고 안내). 씬이 열려 있으면 `EnemyDirector`에서 읽어 오는
편의 경로를 둘 수 있지만 **필수는 아니다**.

>>> (완료) 확정 (2026-08-01)

### 1-6. **배속은 저작값(`ClipAlignment.Speed`)으로 본다**
런타임 배속은 채보 간격과 입력 시각마다 달라진다(`ResolvePlaySpeed`) — 재현할 수 없고,
재현해도 저작 기준이 못 된다.

**저작값 그대로가 저작 기준이다.** 런타임이 압축을 걸지 않는 경우와 프리뷰가 정확히 일치하고,
압축이 걸려도 **임팩트 프레임은 동일**하며 보이는 창만 좁아진다.
배속 상한에 걸리는 경우는 런타임 경고가 잡는다.

화면에 한 줄로 명시해 "이게 실제 재생 속도"라는 오해를 막는다.

>>> (완료) 확정 (2026-08-01)

### 1-7. 루트 모션은 **위치만 잠근다**(기본 켬)
루트 모션이 있으면 `SampleAnimation`이 배우를 밀어내 프레임마다 거리가 변한다 — 배치 확인이 무의미해진다.
루트의 **위치만** 배치값으로 되돌리고 회전은 살린다(방향 전환은 봐야 한다). 토글로 풀 수 있게 한다.

>>> (완료) 확정 (2026-08-01)

### 1-8. **레거시 슬롯은 이 툴에서 뺀다**
`successAnimationClip` + 트림 4필드는 이관이 끝났고(10종 전부 `playerAttack`에 있음)
`Guide_EnemyCombat` 8단계 제거 대상이다. 짝 저작 툴에 섞으면 "어느 게 진짜냐"가 다시 생긴다.

남은 접근 경로는 패턴 인스펙터다. 8단계에서 필드가 사라지면 그것도 없어진다.

## 4. 단계

### Step 0 — 선행: `Pattern.duelDistanceOffset` 신설 + 소비자 통일 (결정 1-10)

**툴보다 먼저.** 저작값이 서야 프리뷰가 진실을 보여준다.

- [x] `Pattern`에 `[SerializeField] float duelDistanceOffset` + `public float DuelDistanceOffset` 게터.
      Tooltip: "결투 앵커 기준 ±m. 이 모션의 리치에 맞춘다. 0이면 씬 앵커 그대로."
- [x] `EnemyDirector.DuelPosition()`을 **패턴 인자를 받도록** 바꾼다:
      ```
      duelAnchor.position + DuelDirection() * template.DuelDistanceOffset
      ```
      호출부는 `HandlePatternQueued`(`AssignAttack`에 넘기는 자리) 하나다.
- [x] `PlaceOnDeck`은 **보정을 적용하지 않는다** — 대기석은 특정 패턴에 묶이지 않는다.
- [x] 기즈모(`OnDrawGizmos`)의 결투 지점은 **보정 없는 기준선**을 그린다.
      패턴별 보정까지 그리면 무엇을 보고 있는지 모호해진다. 라벨에 "기준선"을 명시.
- [x] 슬라이서 휴머노이드 모드의 `결투 거리`를 **기준선 + 패턴 보정**으로 바꾼다.
      **칼 평면 유도가 이 거리를 쓰므로, 어긋나면 유도된 평면 자체가 틀린다.**

### Step 1 — 상태를 배우 2인용으로 재구성
- [x] 마크 상태(`startTime`/`endTime`/`impactTime`/`clip`)를 **배우 구조체 2개**로 묶는다.
      단일 필드가 흩어져 있으면 짝 저작에서 뒤섞인다.
- [x] 입력: `Pattern` / `플레이어 프리팹` / `적 프리팹` / `기준 결투 거리` / `루트 위치 고정`.
      실제 배치 거리는 **기준선 + `Pattern.DuelDistanceOffset`**(결정 1-10). 합계를 화면에 표시한다.
- [x] **`결투 거리 보정`을 배우 블록 위에 편집 가능하게 노출**하고 Apply 때 패턴에 같이 저장한다 —
      맞물림을 보면서 거리를 조정하는 것이 이 툴의 요구사항이다.
- [x] `Pattern` 지정 시 `attacker`로 짝을 해소하고 **두 슬롯을 동시에 로드**한다.
- [x] 슬롯이 비어 있으면 그 배우는 클립 없음으로 두고, 나머지 저작은 계속 가능해야 한다.

### Step 3 — 시간 매핑을 **순수 함수로 분리하고 테스트한다** (조용한 오차 방지의 본체)

시간 매핑이 UI 코드 안에 흩어져 있으면 검증할 방법이 없다. 산술만 떼어낸다.

- [x] `DuetTimeline` 정적 클래스 신설 — **UnityEditor 의존 없이** 순수 산술만.
      `Pattern/Core`(asmdef 보유)에 두어 `Pattern/Tests`에서 바로 테스트할 수 있게 한다.
      ```csharp
      float ClipTimeOf(float impact, float speed, float t)          // 뷰 → 클립 : impact + t*speed
      float RelativeOf(float impact, float speed, float clipTime)   // 클립 → 뷰 : (clipTime-impact)/speed
      (float min, float max) Range(a, b)                            // 스크럽 범위(상대시간)
      float ClampToTrim(float clipTime, float start, float end)     // 트림 경계
      ```
      **배속을 식에 포함한다**(결정 1-2) — 빼면 두 배우의 저작 `Speed`가 다를 때
      "기본 배속 기준"이라는 표시가 거짓이 된다. `speed`는 `ClipAlignment.Speed`(항상 > 0).
- [x] **테스트**(`Pattern/Tests/DuetTimelineTests.cs`):
      - **왕복 항등**: `RelativeOf(imp, sp, ClipTimeOf(imp, sp, t)) == t` (여러 imp·speed·t 조합)
      - **`t = 0` → 배속과 무관하게 정확히 `impact`** (이 프리뷰가 성립하는 근거 자체)
      - 배속이 2배면 같은 `t`에 클립이 2배 진행하는지
      - 범위가 두 배우의 `span`/`tail`을 **상대시간으로 환산해** 합집합인지
        (`span = (Impact − Start)/Speed`, `tail = (End − Impact)/Speed`)
      - 한쪽 배우가 비었을 때(클립 없음) 범위가 나머지 하나로 성립하는지
      - 트림 밖 클램프가 경계값을 반환하는지
- [x] UI는 이 함수들만 호출한다. **산술을 인라인으로 다시 쓰지 않는다** — 그 순간 검증 밖으로 나간다.

## 5. 위험과 대비

> **가장 위험했던 항목(시간 단위 혼동)은 방어가 아니라 구조로 제거했다** — 결정 1-4.
> 아래 표에서 그 줄이 "대비"가 아니라 "해소"로 바뀐 이유다.

| 위험 | 징후 | 대비 |
|---|---|---|
| ~~마크가 상대시간으로 저장됨~~ | ~~저장값이 통째로 어긋남. 조용하다~~ | **해소** — 상태가 이미 에셋 단위라 저장 경로에 변환이 없다(결정 1-4). 남은 변환은 샘플링 한 곳이고 틀리면 프리뷰가 즉시 이상해진다 |
| 시간 산술을 UI에 인라인으로 다시 씀 | 검증 밖으로 새어 나감 | Step 3 — `DuetTimeline`만 호출. 산술은 거기 말고 없다 |
| 저장 경로에 변환이 되살아남 | 조용한 오차 재발 | Step 7 — "상태 그대로 복사" 명시 + 왕복 확인 |
| 한쪽만 저장됨 | 짝이 어긋난 채 남음 | Step 7 — 한 번의 Undo·한 번의 Apply |
| 루트 모션이 배치를 깨뜨림 | 프레임마다 거리가 변함 | Step 2 위치 고정(기본 켬) |
| 결투 거리가 슬라이서와 다름 | 두 툴이 다른 그림 → **유도된 절단 평면이 틀림** | 결정 1-10 — 셋(런타임·합주·슬라이서)이 같은 식 |

| 레거시 제거로 접근 불가 | 구 필드를 못 고침 | 인스펙터로 접근(결정 1-8). 8단계에서 필드 자체가 사라진다 |

## 6. 이 변경이 주는 것

- 절단 평면을 긋기 **전에** 칼이 어디를 지나는지 확인된다 → 슬라이서 6단계 시행착오 감소
- 패링에서 두 칼이 만나는지 **저작 시점에** 판정된다(지금은 플레이해야 안다)
- 두 마크를 **되먹임하며** 조정할 수 있다 — 이게 v1 토글안으로는 안 되던 것이다
- 저작 단위가 채보/코드의 단위(패턴)와 일치한다
- 시간 산술이 **테스트 가능한 순수 함수**로 떨어져 나온다(부수 효과, 결정 1-4)
