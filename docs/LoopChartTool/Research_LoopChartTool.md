# Research — Loop 모드 채보 굽기 (Pattern Chart Tool 이원화)

전제: `docs/StageClearCondition/`(스테이지 종료 조건 개편). 거기서 `StageMode { Loop, Linear }`가 정해졌고, **Linear는 현행 툴을 그대로 쓰고 Loop는 새로 짠다.**

---

## 0. 왜 툴을 갈아엎어야 하는가 — 한 문단

Loop 모드에서는 공격 패턴을 실패하면 채보 시계가 **박의 정수배만큼 되감긴다**(드리프트 `D`). 드리프트가 생긴 뒤, 절대 시각 `t`에 구워 둔 온셋은 **오디오 위치 `(t + D) mod L`**에서 재생된다. `D`는 박의 정수배이고 `L`은 마디의 정수배라 **박자는 계속 맞지만**, 원래 그 자리에 있던 **트랜지언트(스네어·킥)는 더 이상 거기 없다.**

> **즉 온셋 분석의 산출물은 첫 통과에서만 유효하다.** 그리고 첫 통과는 플레이어가 잘할수록 빨리 끝난다 — 온셋 매칭이 가장 오래 살아남는 경우가 가장 짧은 경우다.

현행 파이프라인의 심장이 정확히 그것이다:

```
OnsetDetector.Detect(mono, freq, windowSize, rmsThreshold)   ← RMS 변동이 큰 지점 = 노트 자리
  → BeatGrid.Snap                                            ← 격자에 스냅
  → OnsetGrouper.Group                                       ← 가까운 온셋끼리 묶기
  → OnsetChunkSplitter.Split                                 ← 풀의 노드 개수로 쪼개기
  → PatternTemplateLibrary.GetNextTemplate                   ← 라운드로빈 배정
```

**Loop 모드에서 살아남는 것은 `BeatGrid` 하나뿐이다.** 나머지 넷은 "음악의 이 순간에 노트를 둔다"를 전제하는데 그 전제가 드리프트로 무너진다.

**대체 모델: 격자 저작(grid authoring).** 곡은 균질한 루프 베드이고, 채보는 **마디 격자 위에 손으로 놓는 리듬 도형**이다. 분석이 아니라 저작이다.

## 1. 현행 툴의 구조 (읽은 그대로)

`PatternChartWindow.cs` 1338줄, 단일 `EditorWindow`. `OnGUI`가 일곱 구역을 세로로 쌓는다(동:100~129):

| 구역 | 메서드 | Loop에서 |
|---|---|---|

| 패턴 풀 | `DrawPatternPool`(:145) | **그대로** (역할은 바뀐다 — §3-4) |
| 분석 파라미터 + BPM 격자 | `DrawGridFields`(:205) | **절반 폐기** — RMS·윈도우 크기는 무의미 |
| 액션 버튼(분석/불러오기) | `DrawActionButtons`(:231) | **분석 → 격자 생성**으로 교체 |

| 저장 | `DrawSaveButton`/`Save`(:1262·1277) | **재사용 + 검증 추가** |

### 1-1. 중간 표현(`ChartEntryDraft`)은 모드와 무관하다

```csharp
private class ChartEntryDraft {
    public Pattern template;
    public float[] onsetTimes;          // 절대 시각(초)
    public float[] exposureDurations;
    public float[] spawnTimes;          // 파생 — RecomputeSpawnTimes
    public EnemySpace.EnemyCue enemyCue;
}
```

**이 타입이 두 모드의 접점이다.** Linear는 *분석해서* 채우고 Loop는 *놓아서* 채운다 — 채운 뒤의 편집·검증·저장은 **완전히 공유할 수 있다.** `SongChart` 스키마도 한 필드도 안 바뀐다.

### 1-2. 이미 있는 재사용 가능한 것

| 것 | 위치 | 비고 |
|---|---|---|
| `RecomputeSpawnTimes` | :374~399 | `spawn = onset − exposure`. 노드 수 ≠ 온셋 수면 `spawnTimes = null`로 두고 저장이 막는다 |
| 엔트리 행 편집(템플릿·cue·노출) | `DrawEntryRow` | 그대로 |
| 쪼개기/합치기/연타 변환 | :1135~1210 | **Loop에서는 뜻이 바뀐다**(§3-6) |
| 사슬 일괄 저작 | `chainLength`·`RequiredHits`(:98) | **Loop에서 더 중요해진다**(재시도 단위) |
| `killInterval` 일괄 | :1234~1259 | 그대로 |
| 저장 검증 + 스폰 재계산 | `Save`(:1277) | 그대로 + 검증 추가 |
| 선택/스크롤/`pending` 패턴 | :83~89 | GUI 관용구 그대로 |

### 1-3. Loop에서 죽는 것

- `rmsThreshold` · `windowSize` — 분석 전용 인스펙터 값
- `OnsetDetector` · `OnsetGrouper` · `OnsetChunkSplitter` — **Linear 전용으로 격리**(삭제 아님)
- `maxGroupGapSteps` — 온셋 묶기 파라미터
- `tier1Max`/`tier2Max`/`level → subdivision` 매핑 — **⚠ 반만 죽는다**. `LevelToSubdivision`(BeatGrid.cs:29)은 "레벨이 높으면 잘게 썬다"인데, 격자 저작에서는 **저작자가 스텝 해상도를 직접 고른다.** `level`은 `SongChart`의 표시용 난이도로 남는다.
- `PatternTemplateLibrary.GetNextTemplate`(라운드로빈 자동 배정) — 놓을 때 저작자가 고른다

## 2. Loop가 요구하는 새 제약 (런타임에서 역산)

`docs/StageClearCondition/`에서 확정된 것들이 **저작 단계에 제약으로 내려온다.** 현행 툴은 이 중 **하나도 검사하지 않는다.**

### R-T10. `clip.length`가 마디의 정수배여야 한다 · **치명**
R-L3. 아니면 루프마다 음악이 격자에서 밀리고 바퀴마다 누적된다. **코드로 못 고치고 저작 단계에서만 잡힌다.** 툴은 `clip.length`·`bpm`·`beatOffset`을 전부 들고 있어 계산에 필요한 게 이미 다 있다.

**⚠ `beatsPerBar`가 코드베이스 어디에도 없다.** `BeatGrid`는 `subdivisionsPerBeat`만 안다(BeatGrid.cs:12). 마디를 말하려면 이 값이 새로 필요하고, **런타임도 필요로 한다**(드리프트를 마디로 올림하는 선택지, Plan Step 4).

### R-T11. 엔트리 간 최소 간격이 이제 **저작자 손에 달렸다** · **치명**
§3·§4·R-R10의 분석이 전부 **"엔트리 간 입력 간격 최소 0.4초"**를 전제한다. 지금까지 그 값은 **음악에서 나왔다**(온셋 그룹 간 거리) — 아무도 강제한 적이 없는데 실측상 성립했다.

격자 저작에서는 저작자가 **인접한 스텝에 엔트리 둘을 놓을 수 있다.** 그러면:

- **노드 링이 3개 이상 동시에 뜬다** → R-R10의 "큐에 최대 1개"가 깨진다 → **취소 경로(Step 4-A)가 1개만 회수하고 나머지를 흘린다**
- `handoverIgnoreDuration`(0.08초) 안에 다음 패턴 첫 노드가 들어와 **정상 입력이 삼켜진다**(§3)
- `CharacterActionPlayer`의 복귀 경로가 `minRunExposure`(0.35초) 아래로 내려가 **로코모션이 안 보인다**(§6)

**BPM에 따라 몇 스텝이 0.4초인지가 달라진다** — BPM 120이면 1박(0.5초)이 안전하지만 BPM 180이면 1박이 0.33초라 **2박이 필요**하다. 툴이 BPM을 알고 있으므로 **스텝 단위로 환산해 막을 수 있다.**

### R-T12. `exposureDuration`과 간격이 짝이다 · 높음
R-R10의 "큐에 최대 1개"는 `exposure 0.5 / gap 0.4 / goodWindow 0.1`의 산술이다. 저작자가 노출을 키우거나 간격을 줄이면 **동시에 큐에 오르는 패턴이 2개 이상**이 되어 같은 곳이 깨진다. 지금 `defaultExposureDuration`은 **전역 기본값 하나**(:46)이고 엔트리별로 고칠 수 있는데(:873~880) **아무 검사가 없다.**

### R-T13. 마지막 엔트리가 `Attacker.Player`여야 한다 · 높음
StageClearCondition 결정 6. 저장 차단으로 강제한다. **⚠ `Attacker`는 패턴이 소유해 툴이 못 고친다**(§5) — 자동 보정이 불가능하고 안내만 가능하다.

### R-T14. 사슬이 **재시도 단위**가 되었다 · 높음
사슬 중 하나라도 실패하면 **사슬 머리부터 전체가 다시 나온다.** 즉 사슬 길이가 곧 **실패 시 되돌아가는 양**이다. 지금 툴에서 사슬은 *일괄 버튼*(`사슬로 굽기`)으로만 존재하고 목록에서 뱃지로만 보인다 — **Loop에서는 일급 구조**여야 한다.

덤으로 `chainKillRatio`는 **죽은 노브**가 됐다(모든 타가 결국 성공하므로 언제나 만족). 툴의 `RequiredHits` 표시(:98)가 **거짓말이 된다.**

### R-T15. 채보가 곡보다 길어도 된다 · 중간 · **새 자유도**
Linear에서는 `onsetTimes[^1] > clip.length`가 오류였다. Loop에서는 **곡이 반복되므로 정상**이다 — 채보가 2~3바퀴를 쓸 수 있다. 다만 **저작 화면이 그것을 표현할 수 있어야 한다**(캔버스가 `clip.length`에서 끝나면 안 된다).

### R-T16. 연타(`isMash`)는 격자 저작에서 오히려 쉬워진다 · 낮음
연타 엔트리는 `onsetTimes`가 **창의 시작·끝 둘**뿐이다(§2-1). 지금은 `ConvertToMash`(:1135)가 기존 온셋 배열을 양 끝만 남겨 만든다. 격자에서는 **"이 마디부터 저 마디까지"**가 곧 창이라 자연스럽다. `PatternTemplateLibrary`가 연타를 자동 배정에서 빼는 이유(:61~65)도 Loop에서는 **자동 배정 자체가 없어져** 소멸한다.

## 3. 격자 저작 모델 — 무엇을 놓는가

### 3-1. 좌표계
```
스텝 = beatOffset + k × (60 / bpm / stepsPerBeat)
마디 = beatsPerBar 박
캔버스 = 마디 × barCount   (barCount는 clip.length에서 유도하되, 여러 바퀴로 늘릴 수 있다 — R-T15)
```
`BeatGrid`가 그대로 이 일을 한다(`GridIndexToTime`/`TimeToGridIndex`). **새 수학이 0이다.**

### 3-2. 배치 단위
엔트리 하나 = **(시작 스텝, 노드 간격 스텝, 템플릿)**. 노드 수 `N`은 템플릿이 정하므로 온셋은
`start, start + gap, …, start + (N−1) × gap` — **자동으로 격자 위**다.

- 불규칙 리듬이 필요하면 엔트리의 온셋을 **스텝 단위로 개별 이동**할 수 있게 한다(행 편집).
- 연타는 `(시작 스텝, 끝 스텝)` 둘.

**⚠ 이 모델은 "노드 수 = 온셋 수"를 구조적으로 보장한다** — 현행 툴이 `RecomputeSpawnTimes`에서 검사해 `spawnTimes = null`로 막던 그 불일치(:382~391)가 **표현 불가능**해진다.

### 3-3. 배치는 분석이 아니므로 "재분석"이 없다
현행 `Analyze()`는 드래프트를 전부 버리고 다시 만들며 cue만 인덱스로 되살린다(:250~311). **Loop에는 그 개념이 없다** — 저작물은 저작물이다. 대신 필요한 것은 **격자 파라미터(BPM·beatOffset·stepsPerBeat)가 바뀌었을 때 기존 배치를 어떻게 할 것인가**이고, 답은 **스텝 인덱스를 보존하고 시각을 다시 계산**하는 것이다(BPM을 고치면 채보가 통째로 늘어나거나 줄어든다 — 그게 맞다).

> **⚠ 그래서 드래프트가 스텝 인덱스를 들고 있어야 한다.** `onsetTimes`(초)만 들면 BPM 변경이 배치를 격자 밖으로 밀어낸다.

### 3-4. 패턴 풀의 역할이 바뀐다
Linear에서 풀은 **"자동 배정의 재료"**였다(노드 개수별 라운드로빈). Loop에서는 **"팔레트"**다 — 저작자가 그중에서 골라 놓는다. `AvailableNodeCounts`·`GetNextTemplate`·`GetRandomTemplate`은 Loop에서 안 쓰인다.

### 3-5. 미리듣기가 필요해진다
분석이 없으므로 **"이 리듬이 곡과 맞는가"를 저작자가 귀로 확인해야 한다.** 현행 툴에는 재생 기능이 전혀 없다(파형 그림만 있다). `Tools/Pattern Effect Tool`·`Animation Clip Trimmer`가 이미 에디터 프리뷰를 갖고 있지만 **오디오 재생은 둘 다 안 한다**(§7-4: *"`ParticleSystem.Simulate`는 되감기가 되지만 오디오는 안 된다"*).

- 에디터에서 `AudioClip` 구간 재생은 `AudioUtil` 리플렉션(비공개 API)이나 씬 `AudioSource`가 필요하다.
- **메트로놈 클릭만 찍어 주는 것으로도 대부분 해결된다**(격자가 맞는지 보는 것이 목적이지 믹스를 듣는 게 아니다).

### 3-6. 쪼개기/합치기의 뜻이 바뀐다
현행은 **온셋 배열을 나누고 합친다**(:1154~1210). 격자에서는 **엔트리를 나누면 뒤쪽이 새 시작 스텝을 갖는 엔트리가 되고**, 합치면 두 엔트리의 온셋이 한 템플릿에 들어가야 하므로 **노드 수가 맞는 템플릿이 필요**하다. 기능은 유지하되 **템플릿 재배정을 요구**한다.

## 4. 두 모드를 한 창에 둘 것인가

| 안 | 장점 | 단점 |
|---|---|---|
| **A. 한 창, 상단 모드 토글** | 음원·풀·저장·엔트리 목록을 공유. 모드 전환이 쉽다 | `OnGUI`가 이미 1338줄인데 분기가 늘어난다 |
| **B. 창 둘, 공유 코드 추출** | 각 창이 단순 | 엔트리 목록·저장·검증을 **추출해야** 하고, 그 리팩터가 Linear 툴을 건드린다(회귀 위험) |

**⚠ 어느 쪽이든 `ChartEntryDraft`와 저장 경로는 하나여야 한다.** 둘로 갈리면 저장 검증(R-T10~T14)이 두 곳에 복제되고, 그중 하나만 고치는 날이 온다.

## 5. 모드를 어디에 기록하는가

**⚠ `StageMode`(런타임)와 저작 모드는 다른 물건이다.** `StageMode`는 `GameSession`/`ChartPlayer`가 들고(R-M1: 같은 곡을 두 모드로 플레이해야 하므로 채보에 두지 않는다), 저작 모드는 **"이 채보를 어느 편집기로 열까"**다.

- 기록 안 하면: Loop 채보를 Linear 편집기로 열고 `분석`을 누르면 **저작이 통째로 날아간다.**
- 기록하면: `SongChart`에 필드 하나. **선례가 있다** — `patternPool`이 *"굽기 툴에만 쓰이고 런타임은 안 읽는다"*(SongChart.cs:46).

이름이 `StageMode`와 헷갈리면 안 된다(예: `authoredWith`).

## 6. 결론 — 무엇이 이번 개편의 뿌리인가

1. **온셋 분석은 Loop에서 근거를 잃는다**(§0). 드리프트가 트랜지언트와의 대응을 지우고 격자만 남긴다.
2. **저작 단위가 "음악의 순간"에서 "마디 격자"로 바뀐다.** 분석기가 아니라 **스텝 시퀀서**가 필요하다.
3. **지금까지 음악이 공짜로 보장하던 제약이 저작자 손에 넘어온다**(R-T11·R-T12). 엔트리 간 최소 간격은 §3·§4·R-R10 분석 전체의 전제인데 **아무도 강제한 적이 없다** — 격자에서는 즉시 깨진다.
4. **중간 표현(`ChartEntryDraft`)과 `SongChart` 스키마는 한 필드도 안 바뀐다.** 두 모드는 *채우는 방법*만 다르고 편집·검증·저장을 공유할 수 있다.
5. **새 필드가 둘 필요하다** — `beatsPerBar`(런타임도 쓴다)와 저작 모드 기록.
